# SayClear · 产品技术规划文档

> 项目名：**SayClear**
> Slogan：**读完不算数，说清才算懂。**（If you can't say it clear, you don't get it.）
> 一句话定位：**一个不掌握任何知识、却能倒逼你把读过的书讲清楚的 AI 读书陪练。**
>
> 文档版本：v1.0 ｜ 状态：立项规划 ｜ 更新日期：2026-07-24

## 0. TL;DR（一页速览）

| 维度 | 结论 |
|------|------|
| **它是什么** | 读完书之后，用提问倒逼你把核心观点讲清楚，从而真正内化的 AI 陪练工具 |
| **它不是什么** | 不是判对错的裁判、不是阅读器、不是书库、不是读书社区 |
| **解决的痛点** | 读完就忘、获得感薄弱——输入没有输出，知识没有内化 |
| **核心用户** | 有主动阅读习惯、追求深度吸收、爱输出的高知人群与终身学习者 |

## 1. 解决的痛点

### 1.1 现象
读完一本书之后，对**核心观点、作者背景、知识脉络**的掌握非常模糊，只能记住一个大概。如果读完就不管，不对核心观点做梳理、拆解、深度解析和输出，那么对这本书的实际收获非常有限。

### 1.2 根因（学习科学层面）
这不是"读者笨"，而是一个被反复验证的学习规律：

> **没有输出的输入，几乎不产生内化。**

大脑只有在被迫"重新编码"（复述、解释、举例、反驳）时，知识才会从短期模糊印象转化为可调用的长期理解。读完就走，等于大脑从未做过这次重新编码，所以只剩残影。

### 1.3 现有方案为什么不解决这个痛点
| 现有方案 | 为什么无效 |
|---------|-----------|
| AI 自动总结全书 | 思考的是 AI 不是用户，**获得感更弱**（反疗效） |
| 划线 / 摘抄工具 | 只完成"捕获"，没有"逼输出"，划完照样忘 |
| 读书社区 / 书评 | 解决"讨论"，不解决"个人内化"，且多为浅层观点 |
| 听书稿 / 拆书稿 | 别人嚼碎喂给你，二手知识，内化效率最低 |

**结论**：市面上的产品都在帮用户"更轻松地获取"，而痛点的真正解药恰恰是"更用力地输出"。这是一个被系统性忽略的缝隙。

## 2. 目标用户群体

### 2.1 核心画像
- 有**主动、严肃阅读**习惯（非碎片化刷读）的人。
- 对"读完就忘"有明确的**痛感和不甘**，愿意为深度吸收付出额外努力。
- 认可"输出倒逼输入"，愿意动脑、愿意被"为难"。
- 典型人群：知识工作者、研究者、终身学习者、想把读书转化为认知资产的从业者。

### 2.2 用户特征与产品含义
| 特征 | 对产品的含义 |
|------|------------|
| 阅读来源极其分散（纸质书、Kindle、微信读书、PDF…） | 工具**不能依赖书库**，必须让用户自带素材 |
| 读完想"讲一下"的冲动是碎片化、即时的 | 入口要**低摩擦**（＜3 秒可用），最终主场是手机 |
| 追求认知增值，不追求社交 | **不做社区**，做纯粹的个人工具 |
| 人群相对小众但付费意愿存在 | 商业化走**订阅制**，不追求大 DAU |

### 2.3 明确不服务的人群
- 只想要"快速了解一本书讲了啥"的人（那是听书稿/AI 总结的市场）。
- 想要社交、想找书友聊天的人（那是社区的市场）。

## 3. 意义与价值

### 3.1 对用户的价值
1. **把"读过"变成"读懂"**：通过被迫讲清楚，暴露"以为懂其实没懂"的盲区。
2. **产出可沉淀的认知资产**：每本书留下的是**用户自己的观点卡片**，而非 AI 的总结——带得走、可回看、越攒越厚。
3. **提供稀缺的"啊哈时刻"**：清晰度体检报告精准指出"一问就垮"的地方，这是其它工具给不了的价值锚点。

### 3.2 产品层面的价值（护城河从哪来）
- **单本内化**：谁都能做，是入场券，不是壁垒。
- **跨书的个人知识网络**（V3+）：用户读了 N 本书后攒出的观点体系、冲突检测、观点溯源——**数据越用越厚，别人搬不走**，这才是真正的护城河。

### 3.3 为什么这是"个人开发者能做"的产品
- 定位窄、机制深，是大厂"看不上/懒得做的脏活"，避开正面竞争。
- 技术零风险（核心是一条 prompt 链，不需要囤书库、不需要重后端）。
- 不做社区 → 避开冷启动地狱 → solo dev 可独立扛住。

## 4. 核心设计思想与哲学

### 4.1 第一性原理：模式 B，不是模式 A
产品曾面临一个根本抉择——AI 到底扮演什么角色？

| | A. 事实校验（判对错） | **B. 清晰度逼问（费曼）← 我们选这个** |
|---|---|---|
| 需要标准答案 | 需要（book ground truth） | **不需要** |
| 长尾书覆盖 | 做不到（书太多） | **全覆盖（任何书）** |
| 幻觉风险 | 高（AI 自己都可能记错书） | **低（只判断表达质量）** |
| 心理姿态 | 老师/裁判，让人不敢开口 | **陪练/笨学生，鼓励放心讲** |
| 是否护城河 | 否，且做不好 | **是，且别人懒得做** |

**关键洞察**：判断"讲清楚了没"**根本不需要知道标准答案**。一个没读过《相对论》的笨学生，照样能一针见血地反问"这里我没懂/你前后矛盾了/能举个例子吗"。检测**含糊、术语堆砌、逻辑跳跃、没有自己的例子**这些内化失败信号，是自证的，不依赖 ground truth。

这条洞察一举解决了"全世界书太多、AI 不可能都知道"的死穴——**因为我们压根不需要知道书里写了啥。**

### 4.2 唯一判据：逼产出，而非替产出
> 凡是让用户"读一遍就爽"的功能都是毒药（获得感假象）；
> 凡是让用户"有点难受、要动脑"的功能才是疗效。

任何功能上线前必须回答一个问题：**"它是在逼用户产出，还是在替用户产出？"** 后者一律砍掉（包括 AI 自动总结、AI 自动提知识点、AI 定时总结）。

### 4.3 内化的四个科学机制（功能设计的理论基座）
| 机制 | 通俗说 | AI 的角色 |
|------|--------|----------|
| 主动回忆 Retrieval | 合上书能想起来 | 出题，不给答案 |
| 生成效应 Generation | 自己讲出来才算会 | 追问，判断你讲清没 |
| 精细化提问 Elaboration | 不断问"为什么/凭什么" | 苏格拉底式反问 |
| 间隔重复 Spacing | 隔几天再考一次 | 调度提醒（P1） |

### 4.4 素材来源哲学：用户自带，我们不囤
> **素材由用户带，不由工具囤。**

读完后让用户贴 1–3 句**触动他的原文划线**（粘贴/拍照 OCR/导入高亮）。这带来三重收益：
1. AI 获得了这一场的**局部 ground truth**（不是整本书，是用户认为重要的那几段）。
2. AI 可基于此做更犀利的逼问："你说核心是 X，但你划的三句原文都在讲 Y，是不是漏了？"
3. **"筛选什么重要"这个动作本身就是内化**——把用户的必经动作变成了数据来源，一举两得。

本质上这是**轻量版 RAG**：上下文由用户临时提供，彻底绕开长尾书问题。

### 4.5 Web Search 的定位：佐料，不是主菜
- ✅ 适合：名著/畅销书场景，检索作者背景、成书年代，用来**丰富追问**。
- ❌ 不适合当裁判：书评/网络摘要本身常错、长尾书搜不到、有延迟成本。
- **地基永远是用户自带的原文，Web Search 只是可选增强（P2）。**

### 4.6 三条不可动摇的边界
| 我们是 | 我们不是 |
|--------|---------|
| 逼清晰的陪练 | 判对错的裁判 |
| 读完之后的内化工具 | 读书/看书的阅读器 |
| 用户自带素材的轻工具 | 囤书库 / 搞社区的平台 |

## 5. 产品功能设计

### 5.1 MVP 核心闭环（V1 只做这一条线）

```
① 开一本书（手动输书名，不做书库）
        ↓
② 贴 1–3 句触动你的原文划线      ← 素材来源 + 内化动作
        ↓
③ 费曼闯关：AI 扮笨学生逼问，讲不清就过不去   ← 产品心脏
        ↓
④ 通关 → 沉淀成"我的观点卡片"（你的话，非 AI 总结）  ← 留存资产
```

### 5.2 四个 P0 功能点（V1 必做）

#### P0-1 书架（极简版）
- **是什么**：用户"正在内化的书"列表，手动输入书名+作者即可。
- **作用**：给观点卡片一个归属容器。
- **明确不做**：封面爬取、书库检索、阅读器功能（那是阅读器的活，不是我们的）。

#### P0-2 贴划线（素材注入）
- **是什么**：进入一本书后，先贴/拍/粘 1–3 句原文。
- **作用**：AI 逼问时唯一的"局部 ground truth"；同时让用户重新翻书筛选"什么最重要"，本身即内化动作。
- **V1 实现**：先支持文本粘贴；拍照 OCR / 导入高亮可后置。

#### P0-3 费曼闯关（唯一杀手锏，all-in 打磨）
产品的技术心脏，交互流程：
1. AI 抛第一问："**假装我完全没读过这本书，用 3 句话让我懂它到底在讲什么。**"
2. 用户打字回答（V1 用打字；语音口述留到小程序阶段）。
3. AI 扮演"**听不懂的笨学生**"，专挑**含糊 / 术语堆砌 / 逻辑跳跃 / 与划线不自洽**处反问 2–3 轮。
4. 判定"讲清了"→ 通关；判不清 → 给**清晰度体检报告**（讲清的绿点 / 一问就垮的红点）。
5. **红点 = 用户以为懂其实没懂的盲区**，这是产品的"啊哈时刻"和付费理由。
- **关卡感/游戏化外壳**是完成率的引擎——"讲不清就过不去"。

#### P0-4 观点卡片（留存资产）
- **是什么**：通关后把**用户自己的表述**结构化成一张卡片。
- **结构**：我的核心观点 / 我的例子 / 我还没想清的点。
- **要求**：可编辑、可导出。这是用户唯一带得走、也最想回看的东西。
- **铁律**：卡片内容是**用户产出**，不是 AI 总结。

### 5.3 功能优先级全景

| 功能 | 判据：逼产出？服务定位？ | 裁决 |
|------|------------------|------|
| 费曼逼问追问 | ✅ 产品心脏 | **P0** |
| 闯关模式 | ✅ 逼问的游戏化外壳，提升完成率 | **P0**（作为逼问的形式） |
| 观点卡片沉淀 | ✅ 用户产出物，留存靠它 | **P0** |
| 贴划线原文 | ✅ 素材来源 + 内化动作 | **P0** |
| 书架（极简） | ✅ 卡片归属容器 | **P0** |
| 间隔重复 / 定时重考 | ✅ 逼二次回忆，但依赖已有卡片 | P1 |
| 跨书知识图谱 / 冲突检测 | ✅ 护城河，但需数据积累 | P1 |
| Web 大屏回顾台 | 🔶 管理/回顾场景 | P1 |
| Web Search 补名著背景 | 🔶 佐料，非主菜 | P2 |
| 语音口述内化 | 🔶 手机端杀手体验 | V2（随小程序） |
| AI 自动总结全书 | ❌ 反疗效（替用户产出） | **砍** |
| AI 自动提取知识点 | ❌ 反疗效 | **砍**（或降级为用户自标） |
| AI 定时总结 | ❌ 易变代笔 | **改造为"定时再考你一次"** |
| 读书社区 / 书友讨论 | ❌ 冷启动地狱，solo 扛不住 | **永久搁置 / 极后期** |

## 6. 产品形态与端策略

### 6.1 端选择：分阶段单端推进
| 阶段 | 端 | 范围 | 目标 |
|------|----|----|------|
| **V1（现在）** | **Web（移动优先响应式）** | 仅 4 个 P0 功能闭环 | 验证核心机制能否让人"啊哈" |
| V2 | 微信小程序 | 移植 + 补碎片化场景钩子 | 贴近真实使用时机 |
| V3+ | Web / 小程序 | P1 护城河（图谱、间隔重复） | 留存与壁垒 |

### 6.2 为什么 V1 选 Web（而非理论最优的小程序）
- **开发者本人是 Web 开发者**，熟悉度 = 生产力。solo dev 阶段，"能快速做出来、快速改" > "理论上最贴场景的端"。
- Web 作为验证载体足够，最终主场（小程序）留到机制验证通过后再上。

### 6.3 Web 先行的 3 条工程铁律（避免返工）
1. **移动优先响应式**：V1 Web 本质是"能跑通闭环的验证载体"，不做复杂桌面多栏布局；交互逻辑/布局思路直接复用到 V2 小程序。
2. **核心逻辑与端解耦**：费曼 prompt 链、卡片数据结构、追问状态机抽成独立服务层/API，不与 React 组件缠绕。V2 前端重写，后端与 AI 逻辑原样复用。
3. **V1 不做语音**：桌面端打字更自然，语音留到小程序阶段；V1 把全部精力压在"追问质量"上。

### 6.4 端选择对比（决策依据留档）
| 端 | 是否首选 | 关键理由 |
|----|:---:|------|
| Web（移动优先） | ✅ V1 | 开发者熟悉、可快速验证、迁移成本低 |
| 微信小程序 | V2 | 碎片化+低摩擦+读完即用+免上架，最贴真实使用时机 |
| 原生 APP | ❌ 放弃 | 双端开发+上架+推送资质，solo 承受不起，无不可替代收益 |

## 7. 关键决策备忘（一句话结论集）

1. **定位钉死**：不掌握知识的"逼你讲清楚"AI 读书陪练。
2. **模式 B 不是 A**：判"讲清楚没"，不判"答对没"——绕开"没有标准答案"的死穴。
3. **素材用户带**：贴划线原文即局部 ground truth，绕开"全世界书太多"的死穴。
4. **Web Search 是佐料**：名著场景增强追问，绝不当裁判。
5. **唯一判据**：逼产出的留，替产出的砍。
6. **V1 只做一条线**：书架 → 贴划线 → 费曼闯关 → 观点卡片。
7. **费曼闯关是唯一心脏**：值得 all-in 打磨；其余全部后置。
8. **不做社区**：避开冷启动地狱，保住 solo 可行性。
9. **端策略**：Web 先行（移动优先响应式）→ 小程序 → 护城河功能。
10. **架构铁律**：AI 逻辑与前端解耦，跨端复用。
